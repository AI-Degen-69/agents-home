# Anti-patterns (learned)

Hard-learned operational traps to avoid during triage and model routing:

- **Starting work in a pre-existing worktree/branch without a freshness check.** Always verify divergence from `main` using `git rev-list --count`.
- **Mixing ledger rows, environment caveats, and tree state into one prose report** the operator cannot verify or locate.
- **Treating a skill's silence as permission.** Skills don't fetch, don't check branch freshness, and don't guard remotes.
- **Guard text without an independent tripwire.** Every guard must pair with a concrete command the operator can run in 30 seconds.
- **Pricing without capability.** Routing cheapest-first from `models.md` alone misassigns analysis/review tasks where capability, not price, carries the weight. Pair `references/models.md` (price) with `references/capability.md` (grade + task-class matrix), and never let an `[unverified]` model ship the final step of an irreversible task.
- **Ignoring hard caps.** Quota-gated models (e.g. 1 session/day, weekly caps) must gate worthiness before price is considered; `capability.md` encodes the ceiling per model, and a routing that ignores it spends the day's reserve on a non-worthy task. Always read the per-harness reset window stated under that harness in `models.md` before assigning quota-bound work.
- **Taking vendor "beats the frontier" at face value.** A model card's "beats GPT-X on X bench" claim, without an independent cross-model yardstick (AA Intelligence Index) or cited pass@1 numbers, is marketing signal — routing from it grades models above their independently-verified tier.
- **Hiding score conflicts.** When a model's reported numbers diverge across sources (e.g. a 47.7 partner figure vs a 23 GA-page figure), do not silently pick one — record both, pick the authoritative source, and flag the conflict; a silently mis-graded tier corrupts the whole task-class matrix above it.
- **Hard-coding one worktree path across every task card.** Two sessions on one path clobber each other: one switches the branch under the other mid-task, and the second session's commits land on the wrong branch. The card names the branch; the session owns the path — use the worktree the harness gave that session, or create one with `git worktree add -b <branch> <path> origin/main`, and prove ownership with `git worktree list` before the first edit.
- **Assuming `git switch main` works inside a linked worktree.** The base branch is usually held by the primary checkout, so the switch dies with `fatal: 'main' is already used by worktree at ...` and the closeout's "on the base branch" / "up to date with origin/main" checks can never pass literally there. Detach instead (`git switch --detach origin/main`), delete the branch, delete it on the remote, `git fetch --prune`, then `git worktree remove <path>` — and disclose the deviation.
- **Believing a merge removes a worktree.** `gh pr merge` is remote-only; it touches no local worktree. Station V deletes the branch, Station VI prunes files, and only `git worktree remove` (or `git worktree prune` after the folder is gone) ends a worktree. Treating a merge as the cleanup leaves a stale worktree that the next task picks up by mistake.

- **Hoarding the daily S+ slot for a `perfect` future task.** A daily-reset slot (e.g. FB-10 Argon) that sits unused is wasted budget, not preserved optionality. Route it to the most worthy task available today. If a task clears S-grade worthiness by even a small margin and the slot is open, take it -- the hypothetically `more worthy` task may never arrive, or the slot resets before it does.
- **Silently downgrading a task under a budget constraint without stating why.** When a harness quota or hour pool is limited, every model change must name the constraint in the routing table (e.g. `Freebuff 3h remaining -> FB-4 instead of FB-6`). A downgrade with no explanation looks like a routing error; a downgrade with a named constraint is auditable.
