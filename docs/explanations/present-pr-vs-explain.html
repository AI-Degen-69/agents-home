explain: הסבר עמוק ומדויק של שאלה / שינוי / עיצוב, עם כמה ויזואלים שצריך, כולל מה שלא בטוח — מוצג בלשונית Preview.

PRESENT-PR

הצגת עבודה גמורה ללקוח

  • קהל: לקוח. לא מפתח. בלי קוד, בלי נתיבים, בלי מספרי commit.
  • מילון חובה: PR ← עדכון ששולב, issue ← בעיה/בקשה, verify ← לבדוק שזה עובד.
  • חוק הברזל: רעיון אחד = ויזואל מרכזי אחד. כל השאר תומך או נמחק.
  • אסור לחזור: אם 2 הדפים האחרונים היו before/after, חייבים משפחה + צבע + שלד אחרים.
  • מקור: השינוי האמיתי + השיחה. התיקייה של התוכנית — רק אם יש.
  • שמירה: בתוך הפרויקט, עם מספר + כותרת, ועושים git add מיד.
  • חשיפה: פותחים בדפדפן עם start file.html ועוזבים. בלי לשלוט בדפדפן.
EXPLAIN

הסבר חזותי מלא ומדויק

  • קהל: מי ששאל — חבר צוות, אתה בעתיד, כל מתעניין.
  • מטרה: התובנה הכי מדויקת, לא סקירה כללית. מה שלא בטוח — כתוב בפירוש.
  • חוק הברזל: כמה ויזואלים שבאמת עוזרים: תרשים, זרימה, מפה, טבלה, ציר זמן, דוגמה, אנימציה.
  • איך בונים: משחזרים מהשיחה + ה־diff + הקוד מסביב + מסמכים.
  • טכני: קובץ אחד עצמאי, CSS/JS/SVG inline, רספונסיבי, נגיש, מכבד reduced-motion.
  • שמירה: בתיקיית השיחה, למשל docs/explanations/. לא נוגעים בקוד מוצר.
  • חשיפה: Preview tab + בדיקת צילום, לוגים וחיתוכים לפני שמסיימים.

3. במה לבחור? — לחצו על המצב שלכם

בחרו present-pr. כותרת = מה הלקוח מרוויח (“נכנסים בלחיצה אחת”), לא מה בניתם. ויזואל מרכזי אחד — למשל לפני/אחרי או מספרים גדולים. בסוף: לינק לקובץ + איפה ללחוץ באפליקציה האמיתית כדי לראות.
בחרו explain. תראו את האפשרויות זו מול זו, כולל מה לא בטוח. טבלה + דוגמה קונקרטית + תרשים זרימה עדיפים על דף שיווקי.
בחרו explain. מפת ארכיטקטורה + רצף קריאות + דוגמת קוד קצרה. המטרה דיוק, לא פשטות שיווקית.
כלל אצבע: אם המשפט מתחיל ב־“מה הלקוח מקבל עכשיו?” — זה present-pr. אם הוא מתחיל ב־“איך זה עובד / מה ההבדל / מה לבחור?” — זה explain.
הדף הזה עצמו נבנה בסגנון explain: כמה ויזואלים (כרטיסים + טבלה + תרשים + טאבים) כי המטרה היא דיוק והשוואה, לא סיפור לקוח יחיד.
