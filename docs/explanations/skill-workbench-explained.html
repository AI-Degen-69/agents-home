🔧 Skill Workbench

The front desk for all skills: find → check → review → send → publish. It does not fix things itself — it sends the work to the right helper.

Home: ~/.agents/skills/skill-workbench · Shared by all tools

1. Big picture

Think of a car garage reception. The workbench does not repair the car. It lists all cars, checks what is broken, writes a review, then sends it to the right mechanic.

📋 Inventory→ ✅ Validate→ 🔍 Audit→ 🧭 Route→ 🚀 Deploy

2. Files — what each one does

spec-checklist.md
Rule book. Turns the official spec into checkable IDs. Read before you trust any validator error.
audit-policy.md
How to criticize fairly. Only sure findings, no guessing. Ideas are offered, never hidden-inside.
reporting-contract.md
How to report. Shared with skill-refinement-loop. Progress first, final summary only at end.
validate.js
Zero-dependency checker. Exit 0 = clean, 1 = problems, 2 = wrong use. Single skill or --all, --json for machines.
score.js
Gives 0–100 score. Deterministic. Uses same lib as validator.
inventory.js
One-glance list of every skill in the root. Ranks what to fix first.
evals/evals.json
This skill's own tests. Proves the workbench itself works.

With name — Single-skillYou name one skill, e.g. iii-build-planStep A Validate+Score → Step B Audit → Step C Route → Step D Deploy check. Report after each step.
Validate-onlyQuick checkRun validator, list problems, stop. No audit, no route, no deploy.

4. Score — 5 numbers that drive the choice

MetricWeightWhat it checks
spec-compliance40Frontmatter + structure rules
file-integrity25File links + skill links really exist
eval-readiness20evals/evals.json exists and has prompts
size-discipline10Body ≤250 lines full marks → 0 at 600
self-containment5Has helpers like scripts/, references/

Overall: ≥90 excellent · ≥75 good · ≥50 needs-work · else poor.
Example: spec 100 · files 100 · evals 0 · size 80 · self 100 = 40+25+0+8+5 = 78/100 (good, but eval gap)

Rule: eval-readiness <100 → needs tests. spec/file <100 → fix first. ≥90 with tests → check deploy.

5. Where it sends you (Routing)

If the skill is…Go to
Missing / broken / new ideaskill-creator
Exists but never testedskill-creator (evals) or skill-refinement-loop Phase 1
Has a known failure, needs polishskill-refinement-loop
Clean + testedDeploy check (Step D)

Safety gate: before handing off, the workbench also checks the helper itself with validate.js <helper>. If the helper is broken, fix the helper first.

Deploy check (Step D): only checks links exist with right type (Junction for Claude Code/Hermes, SymbolicLink for Gemini/Antigravity). Prints commands, runs only if you say yes. No final summary before this is done or you skip it on purpose.

6. Hebrew report rule — why it looks strange

Every report line must start with a Hebrew word — that forces right-to-left display. Latin names, paths, commands stay in isolated backticks ⁦`...`⁩. Emoji always after words, never at line start.

דוגמה:
סקיל: ⁦iii-build-plan⁩
נתיב: ⁦C:\Users\Tiger\.agents\skills\iii-build-plan⁩
מצב הסקיל: 2 הפרות, ציון כללי 78/100 (good) 📊
Report sections (fixed order)

תקציר הסקיל 📋 → מצב הסקיל 📊 (+ numeric score) → ממצאי ביקורת 🔍 → שאלות פתוחות ❓ → הצעות שיפור 💡 → ניתוב 🧭 → אפשרויות להמשך 🔀 (3 fixed steps). In Discovery mode the last one is instead הפעולה הבאה 🎯: one recommended skill as the default, alternatives on one line, then halt. Never both, never a recommendation followed by a "pick a number" menu.

7. Review style + fix loop

Findings look like CodeRabbit: table grouped by category (📐 quality, 🗄️ data, ⚡ speed, 🧪 tests, 📝 docs, 🔒 safety), then numbered cards with severity 🔴/🟠/🟡 and effort ⚡/🔧/🏗️. No guessing — each finding needs proof in code or spec.

Fix one-by-one: fix 1 finding → run validate.js must be clean → short progress line in Hebrew (e.g. נותרו 2 ממצאים) → next. No partial final summary. Only when all done + deploy checked → re-run score.js + clean validation → show סיכום סופי (what changed, why it helps, what works now, next step, one-line when-to-use).

8. When to call it

Say “skill workbench” when you want to check / audit / validate / improve a skill, see health of all skills, or know where a skill sits in its life. Dashboard HTML (if made) lives in skills/<name>/docs/workbench-report-<date>.html — never in temp. And the workbench itself must pass its own validator after any edit.
